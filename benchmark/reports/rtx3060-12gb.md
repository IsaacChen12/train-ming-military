## Key Findings

### 1. Rankings differ from Machine A (RTX 4090 Laptop, 16GB)
On the 4090, `qwen3.5:9b` was the clear speed runner-up behind a 7B model, and `qwen3.6:35b` trailed at ~54 tok/s. On this 12GB card, `qwen2.5:7b` (not tested on Machine A) is the fastest by a wide margin, and every larger model lost more ground proportionally — the 35B MoE model in particular fell ~28% due to heavier CPU offload (58% CPU / 42% GPU vs mostly-GPU on the 4090). **Conclusion: model selection must be re-validated per machine, not inherited.**

### 1b. `gemma4:12b` confirms the ~35% "fits-in-VRAM" penalty is consistent
Three models now tested on both machines that fit entirely in VRAM on both (`qwen2.5` 7.6B, `qwen3.5:9b`, `gemma4:12b`) all show generation-speed drops clustered tightly around **-35 to -38%** (-37.7%, -34.8%, -35.7% respectively) going from the 4090 Laptop to the 3060. The only outlier is `qwen3.6:35b`, which needs CPU offload on both machines and drops noticeably less (-27.6%) — reinforcing that raw GPU compute/bandwidth, not offload, drives the gap for fully GPU-resident models. See [rtx4090-vs-rtx3060.md](rtx4090-vs-rtx3060.md) for the full breakdown.

### 2. `qwen3.6:35b` still works on 12GB — no OOM
Unlike `gemma4:26b` (18GB) which OOM'd on the 4090's 16GB in the earlier benchmark, this 22GB MoE model ran to completion on a 12GB card via CPU offload. It's slow (38.79 tok/s) but usable for offline/quality-priority use cases where latency doesn't matter.

### 3. `qwen3.5:9b`'s verbosity is hardware-independent
The "answer a trivial math question with 1000+ tokens" behavior reproduces here exactly as it did on the 4090 — this is a model/prompt-template characteristic (thinking-style output), not a hardware artifact. Deployments should still consider capping `num_predict` or steering the system prompt if terse answers are desired.

### 4. QLoRA fine-tuning headroom on this machine is tighter than Machine A
The project's fine-tune base (`qwen3.5:9b`) is estimated at **10-13GB** VRAM for 4-bit QLoRA training (see RUNBOOK.md). Machine A's 16GB card has comfortable headroom; this machine's 12GB card does **not** — the upper end of that estimate (13GB) would not fit, and even the lower end (10GB) leaves only ~2GB margin. **Training on this machine should reduce `cutoff_len` and/or enable gradient checkpointing, and should be treated as unverified until an actual training run is benchmarked** (this report only covers inference).
